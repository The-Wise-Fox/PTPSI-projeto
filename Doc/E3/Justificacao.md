Normalização
A primeira versão do modelo conceptual corria o risco de agregar dados de diferentes entidades numa única tabela (por exemplo, juntar os dados do serviço diretamente na agenda). Para evitar redundância e anomalias de atualização, o modelo foi normalizado até à Terceira Forma Normal (3FN). Cada facto é guardado num único local: os dados dos utilizadores (utilizador), dos locais (local) e dos serviços (servico) estão isolados. A ligação entre a agenda e os serviços é feita através da tabela agenda_servico. Se um serviço mudar de preço na tabela servico, a alteração reflete-se automaticamente em todas as agendas sem necessidade de corrigir múltiplas linhas. Além disso, tabelas de referência como tipolocal e tipocontrato evitam a repetição de strings (ex: "Apartamento", "Mensal") e garantem a integridade dos dados.

Chaves
Como um serviço pode estar associado a várias agendas e uma agenda pode ter vários serviços (relação N:M), foi criada a tabela de ligação agenda_servico. Apesar de ter uma chave primária própria (id_agenda_servico), esta tabela funciona como o elo de ligação entre as chaves estrangeiras de agenda e servico, permitindo também armazenar atributos específicos dessa relação, como a hora_inicio e a hora_fim. Adicionalmente, a tabela local possui uma restrição de unicidade composta (UNIQUE KEY uk_local_util_email), garantindo que um utilizador não regista o mesmo email para dois locais diferentes. As chaves estrangeiras (FOREIGN KEY) estão declaradas em todas as relações, garantindo que não existem registos órfãos.

Sistema de Gestão de Base de Dados (SGBD)
Escolhemos o MySQL (Community Server). Esta decisão prende-se com o facto de ser um sistema gratuito, open-source e amplamente documentado. Integra-se perfeitamente com o ambiente de desenvolvimento local (XAMPP) e com o backend em Node.js (previsto para a fase E5), através de bibliotecas estáveis. O MySQL permite ainda a aplicação rigorosa de restrições de integridade (NOT NULL, UNIQUE, FOREIGN KEY), o que é essencial para o modelo desenhado.

Limitação Assumida
A tabela utilizador agrega diferentes perfis (admin, gestor, cliente) através de um campo ENUM. Esta foi uma decisão para simplificar o modelo e evitar tabelas quase idênticas. No entanto, se os requisitos futuros exigirem que, por exemplo, os clientes tenham dados fiscais e os gestores tenham dados contratuais muito distintos, o modelo terá de ser refatorado para separar as entidades (herança). Além disso, nos dados de teste as passwords estão em texto limpo (como permitido para testes), mas na implementação do backend serão guardadas apenas em formato hash.
